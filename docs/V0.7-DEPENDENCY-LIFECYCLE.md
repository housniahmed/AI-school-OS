# V0.7 — Layer 5: Dependency Lifecycle & Continuous Monitoring

## Purpose

Layer 5 extends supply-chain controls beyond a single build. The repository continuously checks dependency security, lockfile reproducibility, package freshness, license metadata, and time-bounded security exceptions.

## Controls

- Daily scheduled dependency security monitoring.
- High and critical `npm audit` findings remain merge-blocking.
- Production dependency audits remain enforced by the Security Scanning workflow.
- `npm ci` and `npm ci --dry-run` verify lockfile/manifests remain synchronized.
- `npm outdated` reports available updates without automatically changing production dependencies.
- A license inventory is generated from the committed lockfiles and retained as CI evidence.
- Denied licenses can be configured in `.github/dependency-policy.json`; none are denied until the actual dependency graph has been reviewed.
- Dependency exceptions are explicit, owned, reasoned, uniquely identified, and expire on a fixed date.
- Expired or malformed exceptions fail CI.
- GitHub Actions used by this layer are pinned to immutable commit SHAs.

## Exception policy

An exception does not silently suppress `npm audit`. It records why a finding or dependency risk is temporarily accepted and when that decision must be revisited. Any actual audit bypass must be implemented as a separately reviewed change; it must never be hidden in CI configuration.

Required fields:

- `id`
- `package`
- `reason`
- `owner`
- `expiresOn`

Example:

```json
{
  "id": "SEC-2026-001",
  "package": "example-package",
  "reason": "Vendor patch pending; compensating control documented separately.",
  "owner": "security-owner",
  "expiresOn": "2026-12-31"
}
```

## License governance boundary

The first Layer 5 implementation inventories the licenses declared in `package-lock.json`. It does not declare licenses legally acceptable or unacceptable by assumption. A deny-list should only be populated after the project's dependency graph and distribution model have been reviewed.

## Monitoring cadence

The scheduled workflow runs daily. Push and pull-request triggers provide immediate validation for repository changes.

## Evidence

Each successful run retains:

- API and web `npm audit` JSON reports;
- API and web outdated-package reports;
- consolidated license inventory;
- exception-register validation result.

A successful workflow demonstrates that the controls executed. It does not prove that every package update is safe or that a license is legally suitable for every deployment context.

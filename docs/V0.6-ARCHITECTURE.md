# V0.6 — Production Observability & Reliability Architecture

## 1. Release objective

V0.6 hardens the V0.5 baseline for a controlled production pilot. It is an engineering-readiness release; it does not by itself constitute a compliance certification or a CNDP approval.

## 2. Workstreams

### A. Secrets

Application code must consume secrets through a single configuration boundary. Local development may use `.env`; production must inject secrets from an approved secret manager or orchestrator secret store.

Required production secrets include:
- `DATABASE_URL`
- `JWT_SECRET`
- `REDIS_URL` (if credentials are embedded)
- `OPENAI_API_KEY` when the OpenAI provider is enabled

Rules:
- Never log secret values.
- Never return secrets from health/readiness endpoints.
- Never commit real `.env` files.
- Fail fast when a production-required secret is absent or insecure.
- Keep local-development fallback explicitly distinguishable from production configuration.

### B. Metrics

Expose a Prometheus-compatible metrics endpoint behind deployment-level access control. Initial metrics:
- HTTP requests total by method/route/status class.
- HTTP request duration histogram by route/status class.
- In-flight HTTP requests.
- Readiness state for PostgreSQL and Redis.
- Authentication failures and rate-limit rejections, without usernames/emails in labels.
- AI request/tool execution counts and latency, without prompts, outputs, or personal data in labels.

High-cardinality values such as user IDs, student IDs, invoice IDs, IP addresses and request IDs must never be metric labels.

### C. Tracing

Adopt OpenTelemetry-compatible tracing with W3C Trace Context propagation. OpenTelemetry's JavaScript SDK supports W3C propagation and HTTP instrumentation; the implementation deliberately uses a manual server span so the application's existing `requestId` can be correlated without copying authentication or tenant data into spans. citeturn7search4turn5search3

Every request gets:
- `trace_id`
- `span_id`
- existing `request_id` as a correlation attribute only

The existing request ID remains an application correlation identifier. Trace IDs are for distributed diagnostics. Neither should be used as a substitute for authorization.

Privacy controls:
- Incoming HTTP spans are created by application middleware, not automatic HTTP server instrumentation.
- Only method, normalized route, status and request ID correlation are recorded.
- No request/response body, authorization header, cookie, user ID, tenant ID, IP address or User-Agent is recorded in the application trace span.
- W3C `tracecontext` is enabled; W3C Baggage is disabled so arbitrary key/value data cannot be propagated accidentally.
- Outbound trace propagation is disabled by default. It is enabled only for hostnames explicitly listed in `OTEL_TRACE_OUTBOUND_HOSTS`, which prevents internal trace context from being sent to public/external services.
- Outbound HTTP query parameters have an explicit redaction list covering common credential and personal-data keys. HTTP header capture is disabled.
- Resource auto-detection is disabled by default to avoid exporting host/process/environment metadata unintentionally.
- OTLP export is disabled by default in local development and must be explicitly enabled in a deployed environment.

These controls follow OpenTelemetry's security guidance to avoid sensitive baggage and to consider the risk of propagating internal trace context to external services. citeturn6search9turn6search1

### D. Vulnerability management

CI should scan:
- npm dependencies from the committed lockfile;
- Docker images used for deployment;
- application/container configuration where the selected scanner supports it.

The policy must distinguish newly introduced findings from an accepted baseline. High/critical findings with a practical remediation path block the release.

### E. Backup and disaster recovery

Backups must be:
- encrypted;
- stored separately from the primary database environment;
- retained according to an explicit policy;
- periodically restored in an isolated environment.

RPO and RTO are measured targets, not claims. A restore drill must record backup age, restore duration, validation result and data-loss window.

### F. Privacy engineering

Engineering controls must support the privacy assessment required before a real school deployment:
- data inventory and purpose mapping;
- tenant isolation;
- least-privilege access;
- auditability;
- log minimization;
- retention/deletion policy;
- controlled export where legally and operationally required;
- documented external data transfers and processors.

Do not label the product “CNDP compliant” without the applicable legal review and customer/process-specific status being established.

## 3. Observability data classification

| Data | Logs | Metrics | Traces |
|---|---|---|---|
| route/method/status | yes | yes | yes |
| latency | yes | yes | yes |
| request ID | yes | no | yes, correlation only |
| tenant ID | no | no | no |
| user ID | no | no | no |
| IP/User-Agent | no | no | no |
| request body | no | no | no |
| authorization header | no | no | no |
| student/guardian PII | no | no | no |
| AI prompt/output | no | no | no |
| secret values | never | never | never |

## 4. Release gates

A V0.6 candidate is releasable only when:

1. Production secret handling is explicit and testable.
2. Metrics are useful without high-cardinality or personal-data leakage.
3. Trace propagation works without capturing sensitive payloads.
4. CI performs dependency/container security scanning.
5. Backup encryption/retention and restore evidence exist.
6. RPO/RTO have been exercised and recorded.
7. Privacy/CNDP engineering controls are documented and the product makes no unsupported compliance claim.

## 5. Sequencing

1. Configuration/secrets boundary.
2. Metrics instrumentation.
3. OpenTelemetry tracing.
4. Vulnerability scanning.
5. Backup encryption/retention evidence.
6. DR exercise and measured RPO/RTO.
7. Privacy engineering review.

This sequence intentionally establishes the observability foundation before adding alerting or automated remediation.

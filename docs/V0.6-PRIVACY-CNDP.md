# V0.6 — Privacy & CNDP Engineering Controls

## Status

This document defines engineering readiness controls for deployments in Morocco. It is **not** a CNDP certification, legal opinion, or confirmation that a specific school's processing has been declared/authorized.

The applicable baseline is Morocco's Law 09-08 and CNDP procedures. The school/customer remains the responsible party for determining the purposes and legal basis of its processing and for completing the applicable CNDP formalities.

## 1. Data inventory and classification

### Personal data handled by the product

| Domain | Examples | Classification | Engineering control |
|---|---|---|---|
| Identity | student/staff/guardian names, email, phone | Personal | Tenant isolation, RBAC, audit |
| Student records | student code, date of birth, class | Personal | Tenant isolation, least privilege |
| Finance | invoices, payments, references | Personal/financial | RBAC, audit, restricted exports |
| Operations | maintenance, assignments | Operational; may identify people | Tenant isolation, RBAC |
| Authentication | email, password hash, credentials | Security-sensitive | Hashing, secrets boundary, no plaintext logging |
| AI interactions | user prompts and model outputs | Potentially personal | No prompt persistence in audit logs; external processing gated |
| Observability | request ID, trace ID, method/path/status | Operational metadata | No request body/auth header/PII in logs or traces |

The application must not collect CIN, health data, biometric data, religious/political information or other sensitive categories unless a separately reviewed product requirement, authorization basis and CNDP treatment formalities exist.

## 2. Purpose limitation and minimization

- API request bodies are not written to HTTP logs.
- Authentication headers, cookies and credentials are not written to logs or traces.
- HTTP logs use normalized routes rather than student/user/entity identifiers.
- AI audit events record operation metadata only; raw user prompts are not persisted.
- Metrics use low-cardinality technical labels and do not contain tenant IDs, user IDs or personal data.
- Traces disable header capture, baggage and resource detectors that could introduce host/user metadata.
- Diagnostic redaction exists as defense-in-depth for common direct identifiers.

These controls support the CNDP principles of specified purpose, proportionality and security, but do not by themselves establish lawful processing or CNDP approval.

## 3. Retention

Retention must be configured per data category and customer requirement rather than using one universal deletion period.

Minimum engineering rules:

- Production backups follow the documented backup retention policy.
- Audit logs have an explicit customer-approved retention period and must not be retained indefinitely by default.
- Observability systems must have bounded retention and access controls.
- Data no longer required for the declared purpose must be deleted or anonymized according to the customer's approved retention schedule and applicable legal obligations.
- Legal holds or statutory retention requirements override automated deletion only when documented by the responsible party.

Automated deletion jobs for application data are intentionally not enabled in this release because retention periods are customer- and record-type-specific and must be approved before destructive automation is introduced.

## 4. Data subject rights / controlled hooks

The product architecture must support controlled handling of requests for access, correction, deletion and other applicable rights.

For V0.6:

- tenant isolation prevents cross-school disclosure;
- audit events provide an accountability trail for administrative operations;
- exports/deletions must be executed through authenticated, authorized administrative workflows;
- destructive privacy actions must be audited and require explicit human authorization;
- no anonymous endpoint is provided for bulk personal-data export or deletion.

A production customer onboarding checklist must identify the responsible party, request-verification process, response workflow, retention exceptions and evidence location before these workflows are enabled operationally.

## 5. International transfers and external AI

If personal data is hosted or transmitted outside Morocco, the deployment must complete the applicable CNDP transfer assessment/formalities before production use.

This is particularly relevant when an external AI provider is enabled: prompts can contain personal data supplied by users. External AI processing therefore requires an explicit production configuration acknowledgement and a documented vendor/data-transfer review.

The application must never treat the presence of an API key as proof of CNDP authorization or lawful international transfer.

Recommended production posture for sensitive school data: keep AI processing local or use a deployment/provider architecture that has been reviewed for the customer's CNDP requirements. If external processing is approved, minimize prompts and avoid sending unnecessary identifiers.

## 6. Security and tenant isolation

Privacy controls depend on the security controls already implemented in V0.5/V0.6:

- tenant-scoped queries;
- RBAC and permission checks;
- strong password hashing;
- production secret-manager contract;
- rate limiting and login throttling;
- security headers;
- audit logging;
- encrypted backups;
- restore verification procedure;
- vulnerability scanning;
- trace/log minimization.

## 7. CNDP deployment checklist

Before a Moroccan school enters production:

1. Identify the responsible party and processing purposes.
2. Inventory every personal-data category and recipient/subcontractor.
3. Determine whether each processing requires declaration or prior authorization.
4. Identify any sensitive data or CIN processing requiring the applicable authorization route.
5. Determine whether hosting, backups, AI providers or other subprocessors create an international transfer.
6. Complete the applicable CNDP transfer formalities before such transfer.
7. Define retention periods by data category.
8. Define access roles and privileged administrators.
9. Validate privacy notices/information provided to data subjects.
10. Establish the access/correction/deletion request workflow.
11. Record the CNDP filing/authorization references in the customer's compliance file.
12. Reassess the inventory whenever a new integration, AI provider, data category or processing purpose is introduced.

## 8. Release boundary

V0.6 may claim **privacy/CNDP engineering readiness controls** only.

It must not claim:

- “CNDP compliant” as a blanket product certification;
- CNDP approval for a school/customer that has not completed its own formalities;
- authorization for international transfer merely because contractual safeguards exist;
- legal compliance based solely on technical controls.

Final production approval requires a customer-specific legal/compliance review and evidence of the applicable CNDP formalities.

# V0.7 — Layer 4: Release Governance & Deployment Integrity

## Purpose

Layer 4 separates **validation**, **release authorization**, and **deployment**.

### Release governance controls

- A release must identify an exact 40-character commit SHA.
- The release SHA must be reachable from `sync/v0.3-final`.
- Lockfiles are required and checked before release.
- Release versions use `vMAJOR.MINOR.PATCH`.
- Existing release tags cannot be overwritten.
- Production release execution uses the GitHub `production` environment.
- The workflow uses a concurrency lock so two production releases cannot run simultaneously.
- Release authorization requires an explicit `RELEASE` confirmation input.
- The workflow does not deploy application code.

### Deployment boundary

Deployment remains a separate concern. A deployment workflow should consume only a previously released immutable tag/artifact and should require the production environment approval.

Recommended deployment sequence:

1. CI and security gates pass.
2. Reproducible build passes.
3. SBOM and provenance attestation exist.
4. A human authorizes the exact commit SHA.
5. The immutable release tag is created.
6. Deployment consumes only that tag/artifact.
7. Production environment approval is required.
8. Deployment result is recorded.

### Important limitation

The repository workflow can declare a `production` environment, but required reviewers and branch/tag restrictions must be configured in the GitHub repository settings. They are not safely represented as application code alone.

The current Layer 4 workflow therefore provides the executable release gate without claiming that repository-level approval settings are already configured.

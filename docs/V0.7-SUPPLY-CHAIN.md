# V0.7 — Supply-Chain Hardening

## Layer 3 — Release & Artifact Integrity

This layer establishes release-artifact controls without treating CI success alone as proof of artifact integrity.

### Controls

- Production API and web builds are executed twice from the same locked dependency graph.
- File-level SHA-256 manifests must be identical between both builds.
- Production artifacts are packaged deterministically with normalized archive metadata.
- SHA-256 checksums are published alongside the artifacts.
- GitHub artifact attestations are generated for the API and web production archives on branch pushes.
- Pull requests validate reproducibility but do not create attestations.
- GitHub Actions used by this layer are pinned to immutable commit SHAs.

### Release boundary

The workflow does not publish a production release or deploy it. It produces integrity evidence that a later release/deployment workflow can consume.

### Verification principle

A release process should verify:

1. the source revision being released;
2. the exact lockfiles used;
3. the reproducibility result;
4. the SHA-256 checksum;
5. the artifact attestation;
6. the approval/deployment environment.

A green build alone is not sufficient evidence of artifact provenance.

## Layer 5 — Dependency Lifecycle & Continuous Monitoring

Layer 5 adds daily dependency monitoring, lockfile reproducibility checks, vulnerability gates, license inventory evidence, and expiring dependency exceptions. See `docs/V0.7-DEPENDENCY-LIFECYCLE.md` for the control boundary and evidence model.

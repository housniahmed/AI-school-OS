# V0.6 — Encrypted Backup, Retention & Restore Verification

## Objective

The production pilot requires recoverable PostgreSQL backups, not merely backup files. Each backup must be encrypted, integrity-checked, retained according to policy, and periodically restored in an isolated environment.

PostgreSQL documents `pg_dump`/`pg_restore` for logical backups and recommends actual restore testing in addition to backup verification. For physical backups, `pg_verifybackup` can validate a `backup_manifest`, but it does not replace a restore test.

## Backup format

The implementation uses PostgreSQL custom-format dumps (`pg_dump --format=custom`). They are encrypted with GnuPG symmetric AES-256 using a passphrase supplied through the deployment secret-management boundary.

Required environment variables:

- `DATABASE_URL`: PostgreSQL connection string.
- `BACKUP_DIR`: protected backup working directory or mounted backup volume.
- `GPG_PASSPHRASE_FILE`: path to a temporary/protected file containing the backup encryption secret.
- `BACKUP_RETENTION_DAYS`: retention window; default `35` days for the engineering baseline.

The encryption secret must never be committed, printed, placed in source control, or stored beside the encrypted backup. Production deployments should source it from the approved secret manager/orchestrator secret store.

## Backup procedure

```bash
DATABASE_URL="$DATABASE_URL" \
BACKUP_DIR=/var/backups/ai-school-os \
GPG_PASSPHRASE_FILE=/run/secrets/ai-school-os-backup-passphrase \
BACKUP_RETENTION_DAYS=35 \
bash ./scripts/backup-postgres.sh
```

The script:

1. creates a consistent custom-format PostgreSQL dump;
2. encrypts the dump with AES-256;
3. creates a SHA-256 checksum for the encrypted artifact;
4. removes the unencrypted temporary dump;
5. applies the configured local retention window.

For production object storage, lifecycle/retention rules must also be enforced at the storage layer. The local cleanup in the script is a secondary control, not a substitute for object-storage lifecycle policy.

## Restore verification

A restore drill must use an isolated PostgreSQL instance/database. Never overwrite the production database during a restore test.

```bash
DATABASE_URL="$RESTORE_DATABASE_URL" \
BACKUP_FILE=/var/backups/ai-school-os/schoolos-<timestamp>.dump.gpg \
GPG_PASSPHRASE_FILE=/run/secrets/ai-school-os-backup-passphrase \
bash ./scripts/restore-postgres.sh
```

After restore, verify at minimum:

- PostgreSQL accepts connections;
- Prisma migration metadata exists;
- representative application tables exist;
- a known non-sensitive sentinel record or row count is present;
- application-level health/readiness checks succeed against the restored database.

The encrypted backup checksum is verified before decryption. A successful `pg_restore` is required; validation must then confirm that the restored database is usable rather than merely syntactically restorable.

## Retention baseline

The engineering baseline is:

- daily encrypted backups;
- 35-day operational retention;
- storage-level lifecycle enforcement in production;
- at least one isolated restore drill per release candidate and periodically thereafter.

Final retention periods must be confirmed against the school's contractual, legal, operational and disaster-recovery requirements before a real deployment.

## Security controls

- Backup artifacts are written with restrictive permissions (`umask 077`).
- Plaintext dump files are deleted after encryption.
- Encryption passphrases are supplied outside source control.
- Backup files and checksums must not be exposed through the application, metrics, traces or HTTP logs.
- Backup storage must be separated from the primary database environment.
- Production backup storage should use provider-side encryption in addition to application-level encryption where supported.
- Access to backup storage must follow least privilege and be audited.

## PostgreSQL client security

The backup/restore environment must use a currently supported and patched PostgreSQL client. PostgreSQL published a security fix on 13 August 2026 for a `pg_dump`/`pg_restore`-related vulnerability, fixed in PostgreSQL 18.6, 17.11, 16.15, 15.19 and 14.24. Production images must therefore not remain on affected client versions.

## Restore drill evidence

Every drill should record:

| Field | Required |
|---|---|
| Backup timestamp | Yes |
| Restore start/end | Yes |
| Restore duration | Yes |
| Backup age | Yes |
| Integrity/checksum result | Yes |
| Restore result | Yes |
| Application validation result | Yes |
| Estimated data-loss window | Yes |
| RPO target/result | Yes |
| RTO target/result | Yes |
| Operator/run ID | Yes |

A successful CI restore test proves the procedure works in the test environment. It does **not** constitute production RPO/RTO evidence; that requires a controlled drill against the actual deployment topology and storage path.
